# Test quality audit — does the suite test limits, or confirm behaviour?

> **Scope.** The eight modules of the financial and security core, listed in
> [`scripts/mutation/auditTargets.py`](../scripts/mutation/auditTargets.py).
> **Status: report only.** Nothing under `packages/` and no test file was changed.
> The defects below are documented and prioritised, not repaired.

## The short answer

Mostly it confirms behaviour — but not for the reason a headline count suggests,
and not everywhere.

The two usual suspects are, on measurement, fine. Weak assertions are 12.5% of the
Python suite's `assert` statements and duplicated test shapes are 7.1% of its test
functions (§5). There is no mass of redundant filler to delete, and deleting it
would not have caught anything.

What is wrong is narrower and more serious. In the arithmetic core, several of the
tests this project presents as its hardest — the 1,000-example property tests, the
files named `*Challenger*` and `*Adversarial*` — state their expected value by
copying the implementation's own formula. They will notice if the code changes.
They cannot notice if the code is wrong. That is precisely the shape of defect that
let a statutory GST bug pass a green suite once already, and it is still the shape
of the tests guarding that same module today.

Beside it sits a second, independent problem: guards whose tests enumerate the
inputs the guard already handles, and never the inputs that would defeat it.

## 1. Method, and what it cannot tell you

The score in §2 comes from [`scripts/mutationScore.py`](../scripts/mutationScore.py).
It copies the repository to a temporary directory, introduces one small defect at a
time into the eight core modules — flipping a comparison, shifting a constant by
one, deleting a `raise`, blanking a return — and runs the tests that coverage proves
reach the changed line. A mutant is **killed** if some test fails and **survives** if
the whole selected suite still passes. Every survivor is a change that could be
committed today with a green build. The working tree is never modified.

The operator catalogue is generic and applied mechanically. It is deliberately *not*
a list of the defects this audit found by reading: seeding known bugs would flatter
the result. Two deliberate exclusions push the other way, making the score stricter
rather than kinder:

- `if TYPE_CHECKING:` blocks are not mutated. Negating one forces imports the module
  defers on purpose, which breaks collection rather than testing an assertion — a
  mutant every suite kills for free.
- A mutant that leaves a module un-importable is counted as killed, because the suite
  goes red, but counted **separately** in §2. Nothing about the tests' strength caught
  it; any test at all would have.

**What the score does not measure, which matters more than the number.**

Mutation testing perturbs code that exists. It cannot perturb a guard that was never
written, and it cannot tell you whether the behaviour it is pinning is correct. Two
of the findings below are invisible to it by construction:

- A test that copies the implementation's formula is *maximally* sensitive to
  mutation. Change the code and it disagrees with its own hardcoded copy, so the
  mutant dies. **Mirror anchoring produces high mutation scores.** A high score and a
  tautological test are perfectly compatible.
- A missing guard has no line to mutate. §3.2 is a live bypass in a module whose
  every existing line is pinned.

So read §2 as *how tightly is the current behaviour nailed down*, never as *how
correct is this*. For the second question the only instrument in this repository is
the cross-language differential test discussed in §6.

The harness was checked against a finding established by hand before it was trusted:
§3.6 predicts, from reading, that flipping `<=` to `<` in `verifyWebhookFreshness`
changes behaviour no test asserts. The generic operator set reproduced exactly that
mutant as a survivor, along with three the reading had missed.

### What the 106 survivors are

Sorted, they fall into three groups, and only the first two are test gaps.

**Eight deletable guards.** A `raise` can be replaced with `pass` and nothing objects:

| Module | Guard that can be deleted |
|---|---|
| `arithmeticEnclave.py:59` | `Field '{name}' must be positive integer (> 0)` |
| `arithmeticEnclave.py:76` | `UnitPricePaise cannot be negative` |
| `arithmeticEnclave.py:132` | `Participant ratios list cannot be empty` |
| `arithmeticEnclave.py:242` | `Unsupported type for financial currency normalization` |
| `gstinValidator.py:34,38,44` | The three GSTIN prefix format checks |
| `webhookVerifier.py:52` | `Missing signature or secret` |

Every one of these is a validation guard on the money-and-identity path, and the suite
tests what happens when they pass rather than that they fire. This is the most
actionable line in the report: eight guards could be deleted today with a green build.

**Sixty-one unpinned constants** (58% of all survivors), of two quite different kinds:

- *Schema boundaries* — `gstrInvoiceEngine.py:28-63` is a Pydantic model whose
  `Field(gt=0)`, `Field(ge=0, le=28)` and `min_length` constraints all survive being
  shifted by one. Nothing submits a 29% GST rate or a zero-length SKU id to the
  invoice schema, so its boundaries are declared and never exercised. Real gap.
- *Unused defaults* — `arithmeticEnclave.py:14-21` are the dataclass field defaults on
  `GstBreakdown`. Every caller passes explicit values, so mutating a default changes
  nothing observable. These are effectively equivalent mutants and should be read as
  noise in the score, not as work to do.

**The rest** — 37 comparison flips, boolean swaps and return blanks — overlap the
defects already catalogued in §4.

### The prediction this run falsified

The plan for this audit predicted that the mirror-anchored modules of §3.1 would score
*worst*, on the reasoning that an assertion copying the implementation cannot kill a
mutant of that implementation. **That reasoning was wrong, and the measurement says so
plainly:**

> Not one mutant on `arithmeticEnclave.py` lines 100, 104, 211 or 215 — the four lines
> the property tests transcribe — survived. Every one was killed.

A mirror assertion is *maximally* sensitive to mutation. Change the code and it
disagrees with its own hardcoded copy, so the mutant dies immediately. Mirror anchoring
produces **high** local mutation scores, not low ones. `arithmeticEnclave` still scores
below average (72.5%), but for an unrelated reason: the deletable guards and unpinned
constants listed above, which sit nowhere near the formula.

The two properties are orthogonal, and the clearest evidence is the top of the table.
`callbackUrlValidator.py` scores **100%** — every mutant caught, no survivors — while
accepting the seven loopback and metadata URLs of §3.2. A perfect mutation score and a
live SSRF bypass, in the same file, at the same time. The tests pin every line that is
there; the bypass needs a line that is not.

## 3. Findings

### 3.1 The property tests assert the implementation, not the specification

`tests/property/test_property_enclave_math.py` runs 1,000 Hypothesis examples per
property and then states the expected value as the code's own expression:

```
line  93   assert res.totalTaxPaise == 2 * ((amount * rate_bps) // 20000)
line 110   assert res.totalTaxPaise == 2 * ((amount * rate_bps) // 20000)
line 126   assert res.totalTaxPaise ==     (amount * rate_bps) // 10000
line 137   assert res_intra.totalTaxPaise == 2 * ((amount * rate_percent) // 200)
line 143   assert res_inter.totalTaxPaise ==     (amount * rate_percent) // 100
line 236   assert tcs_intra["tcsCgstPaise"] == (subtotal * tcsCgstBasisPoints) // basisPointsDivisor
line 242   assert tcs_inter["tcsIgstPaise"] == (subtotal * tcsIgstBasisPoints) // basisPointsDivisor
```

Lines 236 and 242 are a literal hand-copy of `arithmeticEnclave.py:211` and `:215`.
The GST assertions go one step further: `arithmeticEnclave.py:100` and `:104` call
`_divideWithRounding(b * rb, intraStateHalfBpsDivisor, rounding_mode)`, and the test
writes out the same computation with the named divisors inlined as `20000` / `10000`
*and* the FLOOR branch hardcoded as `//`. It pins the rounding mode it never varies.
The same pattern recurs in `testMilestone2ChallengerMathCrypto.py` (lines 106, 107, 114–116,
134, 137), `testAdversarialChallenger1MathCrypto.py` (106, 110) and
`e2e/testTier1Coverage.py:173`. A thousand examples of a tautology is still a
tautology: the assertion and the code cannot disagree, because they are the same
expression written twice.

`tests/fixtures/gstGoldenVectors.json` makes it visible. Its `rule` field states the
implementation's formula verbatim, and its vectors use round values — 100,000 paise
at whole-percent rates — that divide exactly. Exactly one vector (100030) exercises
rounding at all. These are golden vectors derived from the code, not from a
statutory source.

**What goes unasked as a result.** Nothing in the suite compares the two GST paths
against each other. They disagree:

```bash
python -c "print(sum(1 for a in range(4000) for b in (25,150,300,500,600,1200,1800,2800) if 2*((a*b)//20000) != (a*b)//10000))"
```

→ `16000` divergent (amount, rate) pairs below 4,000 paise. On a 7-paise line at
18%, intra-state supply is taxed 0 and inter-state 1. Whether that is correct is a
statutory question. The point is that no test asks it, and the tests that look like
they would cannot, because they are anchored to the answer.

There is a structural tell. The previous GST fix was never defended by a test at all --
it was defended by a **grep over documentation** for the superseded formula, and that
grep has since been removed along with the rest of the automation. INV-02 is currently
*defined as* the formula, which is why transcribing it looks like verification, and
nothing now stands between the old formula and the docs it used to live in.

### 3.2 The SSRF guard's tests enumerate its denylist

`tests/testCallbackUrlSsrfGuard.py` parametrises 16 URLs — thirteen it must reject
(lines 26-38), three it must accept (51-53). Every one is a case
`callbackUrlValidator.py` visibly handles. None attacks it:

```bash
python -c "
from razoragentMesh.packages.x402Gateway.src.schemas.callbackUrlValidator import validateCallbackUrl as v
from razoragentMesh.packages.x402Gateway.src.gatewayExceptions import UnsafeCallbackUrlException as U
for u in ['https://2130706433/h','https://0x7f000001/h','https://127.1/h','https://017700000001/h','https://localhost./h','https://metadata.google.internal./h','https://100.64.0.1/h','https://localhost/h','https://127.0.0.1/h']:
    try: v(u); print('ALLOWED', u)
    except U: print('blocked', u)"
```

The first seven are ALLOWED; the last two are blocked, which is what makes this a
bypass rather than a design choice — the guard intends to stop exactly these hosts.

| URL | What it reaches |
|---|---|
| `https://2130706433/` | 127.0.0.1 in decimal-integer form |
| `https://0x7f000001/` | 127.0.0.1 in hex |
| `https://127.1/` | 127.0.0.1 in short form |
| `https://017700000001/` | 127.0.0.1 in octal |
| `https://localhost./` | loopback — bare `localhost` **is** blocked |
| `https://metadata.google.internal./` | GCP metadata — the undotted form **is** blocked |
| `https://100.64.0.1/` | RFC 6598 CGNAT space |

`_isUnsafeIpLiteral` delegates to `ipaddress.ip_address(hostname)`, which raises
`ValueError` for every literal that is not a dotted quad and so reports "not
unsafe". `_unsafeHostnameDenylist` is an exact-match `frozenset`, so a single
trailing dot — which every resolver treats as the same name — walks past it. The
IPv6 and dotted-quad cases are handled correctly.

This is reachable from the API: the guard is wired into `alertSchema.py` as a
Pydantic `field_validator` on the price-drop alert registration route.

### 3.4 The canonicaliser leaks raw exceptions and collides on key types

`canonicalizeJson` is the signing boundary for the entire mandate chain: every
`Ed25519Signer.signPayload`, every `mandateFactory` call, both SDKs.

**`Decimal` defeats the float guard.** `_verifyNoFloats` rejects `float` but not
`Decimal`, and `Decimal` is a type this codebase puts in its own product schemas:

```bash
python -c "
from razoragentMesh.packages.mandateEngine.crypto.jcsCanonicalizer import canonicalizeJson
from razoragentMesh.packages.merchantApi.src.schemas.universalProductSchema import JewelryFacet
from decimal import Decimal
try: canonicalizeJson(JewelryFacet(purityCarat=22, grossWeightGrams=Decimal('12.5'), hallmarkNumber='HM123456'))
except Exception as e: print(type(e).__module__ + '.' + type(e).__name__ + ':', e)"
```

→ `builtins.TypeError: Object of type Decimal is not JSON serializable`. The guard
exists precisely to reject non-integer money types, and this one walks through it.

**Key coercion collides.** `jcsCanonicalizer.py:52` applies `str(k)` before sorting,
so two structurally different payloads canonicalise — and therefore sign —
identically:

```bash
python -c "
from razoragentMesh.packages.mandateEngine.crypto.jcsCanonicalizer import canonicalizeJson as c
print(c({1:'x','1':'y'}) == c({'1':'y'}), c({1:'x','1':'y'}))
print(c({True:'p','True':'q'}))"
```

→ `True b'{"1":"y"}'` and `b'{"True":"q"}'`. Pydantic models constrain keys to
strings and JSON parsing only yields string keys, so this is latent rather than
exploitable today — but it is a silent collision in a signing primitive, and nothing
tests for it.

### 3.5 The rounding convention is unpinned, and the enclave is inconsistent with itself

`calculate_gst` takes `rounding_mode` and defaults to `"FLOOR"`. No production call
site passes anything else. Meanwhile `normalize_inr_to_paise`, in the same file,
uses `ROUND_HALF_UP`. Two conventions, one enclave, no test relating them.

Against an independent half-up `Decimal` oracle the enclave disagrees on most
inputs, and the two paths disagree by different amounts — the intra-state path
floors the half and *then* doubles, losing up to two paise where the inter-state
path loses one:

```bash
python -c "
from decimal import Decimal, ROUND_HALF_UP
from razoragentMesh.packages.mandateEngine.verification.arithmeticEnclave import calculate_gst
rates=(25,150,300,500,600,1200,1800,2800); intra=inter=n=0
for t in range(1,20001):
    for r in rates:
        n+=1
        o=int((Decimal(t)*Decimal(r)/Decimal(10000)).quantize(Decimal('1'),rounding=ROUND_HALF_UP))
        intra+= calculate_gst(t,r,'29','29').totalTaxPaise!=o
        inter+= calculate_gst(t,r,'29','27').totalTaxPaise!=o
print(f'compared {n}, intra diverges {intra} ({100*intra/n:.1f}%), inter diverges {inter} ({100*inter/n:.1f}%)')"
```

→ `compared 160000, intra diverges 119600 (74.8%), inter diverges 79200 (49.5%)`.
At 2 paise and 28%, the enclave charges 0 intra-state where a half-up oracle charges 1.

Flooring is defensible; it under-collects, which favours the buyer. The finding is
not that floor is wrong. It is that **the choice is nowhere justified and nowhere
tested against an external source**, so if it is wrong, every test agrees with the
wrong answer — which is exactly how the earlier GST defect survived a green suite.

One test does touch the parameter. `tests/unit/test_m1_challenger_stress.py:227`
picks `rng.choice(["FLOOR", "HALF_UP"])` inside a 5,000-iteration loop and then
asserts only relational invariants — `cgst == sgst`, `cgst + sgst == total`,
`igst == 0`. Those hold under either mode. The test randomises the one parameter it
is blind to.

### 3.6 Boundary tests that stop one step short

`tests/testWebhookVerifier.py` bounds the window from outside and inside but never
lands on the edge. It asserts `now - 10` and `now` are fresh (lines 38-39) and that
`window + 1` is stale on both the past and future sides (lines 45-46, 52-53). It
never asserts `now - window` or `now + window` — the inclusive edge itself.
`verifyWebhookFreshness` compares with `<=`, so changing it to `<` alters behaviour
at exactly one input, which no test pins. The mutation run confirms the flip
survives (§2).

The same file shows a third form of the anchoring problem in §3.1. Line 11 imports
`webhookFreshnessWindowSeconds` and every expectation is computed *from* it —
`stale = now - (webhookFreshnessWindowSeconds + 1)`. The test therefore cannot
disagree with the constant, whatever it is set to, which is why the mutation run
carries `300 -> 301` as a survivor. Importing the constant is the right instinct for
avoiding a magic literal and the wrong one for pinning a value: something, somewhere,
has to assert that the window is 300 seconds because a specification says so.

Worse, the run also carries the deletion of the missing-credential `raise` as a
survivor (§2): `verifyRazorpayWebhookSignature` can be stripped of its "Missing
signature or secret" guard entirely and the suite stays green. Every call in the
test file passes a real signature and a real secret, so neither outcome of that
branch is ever exercised.

Compare `tests/testNonceLedger.py:56-66`, which pins 994 / **995** / **1060** / 1061
around a `[T-5, T+60]` window — both inclusive edges and both first-excluded values.
The standard already exists in this repository; it is simply not applied uniformly.

## 5. What the suite already does well

Three patterns here are the answer to the rest of it, and each has a working
exemplar:

- **`tests/testCrossSdkTsPyCompatibility.py`** — real differential testing. It signs
  in TypeScript and verifies in Python, and `testGstCrossLanguageEquivalence` runs
  the GST vectors through both implementations. Two independently written
  implementations checking each other is the only oracle in this repository that is
  not anchored to a single codebase's opinion. This is the pattern to extend.
- **`tests/testNonceLedger.py:56-66`** — boundary-value analysis done properly: both
  inclusive edges and both first-excluded values, on both sides of the window.
- **`packages/mcpServer/test/pricingEngineStressEdgeCases.test.ts`** — feeds
  genuinely hostile values (`NaN`, `Infinity`, `1.0000000000000002`) and asserts on
  the specific error message rather than that something was thrown.

And the two structural worries that prompted this audit are, on measurement,
unfounded — the suite is neither padded nor weakly asserted:

| Measurement | Result | Command |
|---|---|---|
| Weak assertions (bare name, `is None`, `isinstance`, `len(...)` comparison) | 363 of 2,894 = **12.5%** | `python scripts/assertionAudit.py` |
| Duplicated test shapes (identical bodies once names and constants are blanked) | 64 of 900 test functions = **7.1%** | `python scripts/assertionAudit.py` |
| Over-broad `pytest.raises(Exception)` / `(BaseException)` | 3 | `grep -rnE "pytest\.raises\((Exception\|BaseException)\)" tests/ packages/buyerSdkPy/tests/` |
| TypeScript truthy-only `assert.ok(...)` | 347 of 1,526 assertions = **23%** | `grep -rhoE "assert\.(ok\|equal\|deepEqual\|strictEqual\|throws\|match\|rejects\|notEqual)" packages/*/test/*.ts \| sort \| uniq -c` |

Both percentages move with their definition, which is why the definitions live in
the script's docstring rather than in this sentence. Neither is a defect on its own:
a bare `assert isinstance(...)` after a specific assertion is fine, and most of the
duplicate groups are the same test shape with different boundary constants —
parametrisation written out longhand, not redundancy. The claim that only a few
hundred of the tests are non-redundant is not supported by structural duplication.

For the suite inventory itself, run `python scripts/countTests.py`. This document
quotes no test count, deliberately: the count is the metric that made the original
GST defect look impossible.

## 6. The one structural change worth making

**Stop defining INV-02 as a formula.** It is currently stated as
`CGST = SGST = floor((Taxable × Rate) / 200)` — in the guide, in the golden-vector
fixture's `rule` field, and transcribed into seven property assertions. When the specification *is* the expression, a test that repeats the
expression looks like verification and is not.

State it instead as a relation an independent oracle can check:

1. Write a reference implementation in `Decimal` at full precision, from the
   statutory text, in the test tree — importing nothing from `arithmeticEnclave`.
2. Assert the enclave agrees with it across the statutory slabs, with the rounding
   rule (S1) named explicitly in the assertion.
3. Extend `testGstCrossLanguageEquivalence` to carry the vectors where the two
   implementations *could* diverge — small amounts, odd rates, the intra/inter
   comparison of §3.1 — instead of round numbers that divide exactly.

The first of those three would have caught the original GST defect. Nothing in the
suite currently would.
